# Editors: Zed and aider

Two tools, deliberately. They are good at different halves of the work and both
address roles rather than model names, so neither needs touching when a model
changes.

| | aider | Zed |
|---|---|---|
| Where | terminal | editor |
| Unit of work | a diff you approve | inline edits and agent runs |
| Best for | changes you want to review before they land | exploring, refactoring in place |
| Agent | n/a — it always shows you the diff | yes, with restrictable tools |

---

## aider

### Config

```yaml
# ~/.aider.conf.yml
# Roles, not model names. OPENAI_API_BASE + OPENAI_API_KEY come from
# scripts/aliases.zsh per invocation. One local model (ADR 0016, D1).
model: openai/local-main
weak-model: openai/local-main
dark-mode: true
auto-commits: true
map-tokens: 4096
```

`weak-model` is used for commit messages and summaries. With one resident
model there is nothing cheaper to point it at, and nothing to evict.
`ask-cloud` overrides both with the Gemini id from `config/roles.tsv`, so a
cloud session never sends its commit messages anywhere else.

### Architect mode

aider can split planning from editing. With one local model both sides are
`local-main`; the value left is that the design step stays visible.

```bash
ask-arch    # aider --architect --model openai/local-main --editor-model openai/local-main
```

`ask-deep` runs aider on `local-deep`, a slower, more careful model, loaded
beside `local-main` for that session (ADR 0020, 0028). It is also in Zed's
model picker, labelled "load first": a request to an unloaded role can be
answered by whatever is loaded, without saying so. To use it from Zed, run
`scripts/demand-load.sh local-deep up` on the host, and
`scripts/demand-load.sh local-deep down` when done. `local-main` stays loaded.

### Switching mid-session

```
/model openai/local-main       the only local role
                              (cloud: quit and start `ask-cloud` instead —
                               it uses its own key and endpoint)
/ask                          question without editing anything
/architect                    toggle architect mode
```

`/ask` is worth the habit — it answers without proposing a diff, which keeps you
deciding what to change.

### Deliberate review

You have `auto-commits: true`, which is convenient and also the setting most
likely to let a change land without you reading it. For anything touching
flagged sensitive code:

```bash
aider --no-auto-commits
```

## Zed

### Point it at oMLX

Directly in `~/.config/zed/settings.json` (ADR 0016). Every model slot —
agent, inline assistant, commit message, thread summary, compaction,
subagent — is `hearth/local-main`, so nothing ever asks for a second model.
**No cloud provider on this host (D3)**: cloud is `ask-cloud` in a terminal.

```json
{
  "agent": {
    "default_model":          { "provider": "hearth", "model": "local-main" },
    "inline_assistant_model": { "provider": "hearth", "model": "local-main" },
    "commit_message_model":   { "provider": "hearth", "model": "local-main" },
    "thread_summary_model":   { "provider": "hearth", "model": "local-main" },
    "compaction_model":       { "provider": "hearth", "model": "local-main" },
    "subagent_model":         { "provider": "hearth", "model": "local-main" },
    "auto_compact":           { "enabled": true, "threshold": 110000 }
  },
  "language_models": {
    "openai_compatible": {
      "hearth": {
        "api_url": "http://127.0.0.1:1234/v1",
        "available_models": [
          { "name": "local-main", "display_name": "<written by scripts/zed-sync.sh>", "max_tokens": 131072 }
        ]
      }
    }
  }
}
```

Automatic compaction runs at 110,000 tokens. The loaded window is 131,072.
Past that the server refuses the prompt, and Zed compacts on that error.
110,000 leaves about 21,000 tokens for the turn that crosses the line and
for Zed's count running behind the server. Zed's default of 90% (about
118,000) sits inside that lag. Compaction summarizes the older turns, sends
that summary plus the recent turns, and leaves the original thread in the
panel under **Context Compacted**. `/compact` does the same by hand.
**New From Summary** starts a fresh thread from it. The summary replaces the
cached prefix, so the next turn reads the new thread from the start.

`name` is the role and is what Zed sends. `display_name` and `max_tokens`
are generated by `scripts/zed-sync.sh` from `config/roles.tsv`, so the
window matches the role's context. Preflight warns if they drift. Add a
new role's entry by hand once; the sync keeps it current.

The token goes in through the UI (Agent panel → settings → `hearth` → API
key) so it lands in the keychain rather than a dotfile. Use the host token on
this machine; each laptop gets its own (phase 4).

### MCP example: auslaw

`auslaw` is not installed. `docs/MCP.md` uses its former setup as a worked
example: a reviewed stdio child, no jade cookie, seven AustLII tools exposed
only in a Research profile, and confirmation before each call.

Zed's built-in **Write** profile sets `enable_all_context_servers: true`
(Zed 1.26 defaults), which would expose any configured server in an ordinary
thread. Settings must redefine Write with that set to `false`. A profile
override **replaces** the built-in profile (`name` is required, tools are not
merged), so the override must carry the full intended tool list. Re-check
Write and Ask after a Zed upgrade: a partial override can fail the whole
settings load. `tool_permissions.default` is `confirm`, so each MCP call asks
first.

If auslaw is restored, switching to Research is the act of saying "this query
goes to AustLII." Follow the prerequisites, UI fields, JSON profile and checks
in `docs/MCP.md`; do not infer a command from this document.

Write and Ask set `fetch` and `search_web` to false. Zed's built-in Ask
profile includes both, so Ask is overridden here the same way Write is.
Search is the Web profile, or Write + search when the thread also edits.

### MCP: searxng

`searxng` is a `context_servers` stdio entry for the pinned SearXNG MCP
server (`docs/MCP.md`, ADR 0022, 0029). Its search tool sends the query text
through the host's SearXNG to public engines. Only `searxng_web_search` is
on. `web_url_read` (any URL) and the other two tools stay off. Each tool
call asks first.

**Web** has an empty built-in tool map and `default_model` `hearth/local-main`.
A search result cannot read a file.

**Write + search** (`write-web`) has Write's tools and no pinned model, so
the thread stays on `local-main` or `local-deep`. It can read files and put
them into the query. It is not the default profile.

Switching to either profile is the act of saying "this query goes to the
search engines". Write + search can read a file and put personal information
from it into that query.

### On a laptop

Through an SSH tunnel to the host — `docs/LAPTOP.md`. Zed points at
`http://127.0.0.1:1234/v1` exactly as on the host (the tunnel's local end),
with the **laptop's own** token. Run `ai-tunnel` before opening Zed. A Gemini
provider is allowed on the laptop (D3). Web stays on `hearth/local-main`.
Write + search has no pinned model. Do not switch either profile to Gemini.

Zed's SSH remote projects also work: edit files on the host over SSH while
the model call goes through the tunnel. That needs a normal SSH key, not the
tunnel-only one.

### Thinking

Thinking for `local-main` is set on the server by `scripts/omlx.sh`
(`docs/MODELS.md`), and healthcheck fails without it. Leave
`enable_thinking` out of `agent.default_model`. In Zed 1.27 an
`openai_compatible` model supports thinking only if its `available_models`
entry sets `reasoning_effort`; without that, `enable_thinking` is forced off
and no reasoning field is sent, so the server default applies (read from
`crates/language_models/src/provider/open_ai_compatible.rs` at v1.27.0).
Adding `reasoning_effort` would change that: `enable_thinking: false` would
then send effort `none`. Do not add it.

### Edit prediction

Three choices. Default is off. Host oMLX does not serve edit prediction
(ADR 0033 amend: the 2026-11-07 paired gate failed).

**1. Off (default).** Safe for every buffer. Zed 1.27 key:

```json
{ "edit_predictions": { "provider": "none" } }
```

On the Free plan, `"provider": "zed"` still posts to Zed and gets 403 — the
request has already left (this laptop's Zed log, 2026-10-31). Keep `none`
until you pick an option below.

**2. Laptop `local-edit` (local).** Build weights
(`docs/MODELS.md` → *Building `local-edit`*), then
`client/edit-model.sh laptop-up` and `client/edit-model.sh bench`. Point Zed
at the laptop's own oMLX (port 8000 by default):

```json
"edit_predictions": {
  "provider": "open_ai_compatible_api",
  "open_ai_compatible_api": {
    "api_url": "http://127.0.0.1:8000/v1/completions",
    "model": "local-edit",
    "prompt_format": "sweep",
    "max_output_tokens": 512
  }
}
```

The key goes in through the UI (status bar edit-prediction menu → Configure
Providers → OpenAI-compatible API key), so it lands in the keychain — use the
laptop oMLX's own key. Works with the tunnel down. Do not point this at the
host through the tunnel: host `:1234` does not load `local-edit`, and when it
did, agent c3 starved predictions.

**3. Paid Zed Zeta (cloud).** With a paid Zed plan, `"provider": "zed"` uses
Zed's hosted Zeta. Cursor context leaves the machine. Allowed only for
buffers that `docs/ROUTING.md` would send to cloud — never for sensitive,
PII, credentials, or flagged repos (rule 3). `scripts/zed-sync.sh --check`
(and preflight) still report DRIFT for `"zed"` on purpose: enabling it is
an operator override, not a green path. Do not add Zeta (or any other cloud
model) as a host Zed language-model provider.

`client/edit-model.sh` is the one script a laptop runs for option 2: it
writes only `~/.hearth/models` and the laptop's own oMLX.

### Sandbox (Zed 1.14)

Since Zed 1.14 (August 2026) the agent panel's **terminal and fetch tools**
run sandboxed by default: no writes outside the project or to `.git`, no
network. It does **not** cover the edit tool, MCP servers (so not
`searxng`), ACP agents, the normal terminal, or LSP servers. It complements
`tool_permissions`; it does not replace `scripts/sandboxed.sh` for aider.

`agent.sandbox_permissions.network_hosts` widens it. Every host listed
there is an egress path for an injected agent (`docs/THREAT-MODEL.md`,
accepted risk 1). Keep it empty on the host; on a laptop, list only what a
thread needs and say why.

### External agents (ACP)

Zed can run other vendors' agents (Claude Code, Codex, Gemini CLI and others)
over the Agent Client Protocol, installed from the ACP Registry. None of the
controls above apply to them: profiles and `tool_permissions` govern only
Zed's own agent, the sandbox does not cover them, and they call their own
cloud with their own keys. Zed may also forward its MCP servers to them.

**No ACP agent on the host.** On a laptop one is a cloud tool like
`ask-cloud`: non-sensitive repos only.

### Agent profiles — the reason Zed is here

Zed's agent has **profiles with configurable tool access**. You can define one
that reads and proposes but cannot apply edits or run commands, and a separate
one that can.

That is the closest thing shipping today to an assistant that helps without
taking over, and it is why Zed earns its place here. JetBrains now runs its
agent on local models too (see *Other editors*), but Zed's profiles are the
finer-grained control.

Suggested split:

- **explore** — read files, search, discuss. No edits, no terminal. Use when you
  are trying to understand something.
- **build** — full tools. Use when you already know what you want.

The distinction is not about safety. It is about which mode you are in.

## JetBrains AI Assistant

Optional. Calls `local-main` the same way Zed does. On a laptop the tunnel
must be up (`ai-tunnel`).

1. **Host:** a key for this IDE, so it can be revoked on its own:
   `scripts/omlx.sh sub-key add jetbrains-<laptop>` (prompt does not echo).
2. **IDE:** Settings → Tools → AI Assistant → Providers & API keys →
   **OpenAI Compatible**. Base URL `http://127.0.0.1:1234/v1`. Type the key
   into the API key field; the IDE keeps it in its own password store.
   **Test Connection**.
3. **Assign the model by hand.** Models from an OpenAI-compatible endpoint
   are not assigned to features automatically. Pick `local-main` for chat
   and each feature you use. Never `local-deep` unless it is loaded.
4. **Offline mode on** for sensitive repos, and no cloud provider or JetBrains
   AI subscription model on the host (rule 3). A feature with no local model
   assigned may use JetBrains' cloud if a subscription is signed in.

Not verified against oMLX: whether Test Connection passes oMLX's token check,
and whether Junie uses a local provider from the IDE or only from Junie CLI.
One JetBrains IDE configures all of them only if settings sync is on; each
IDE otherwise needs steps 2–4.

## Xcode 27

Optional. Swift work only.

1. **Host:** `scripts/omlx.sh sub-key add xcode-<laptop>`.
2. **Xcode:** Settings → Intelligence → Add a Chat Provider → **Internet
   Hosted**. URL `http://127.0.0.1:1234` (no `/v1`: Xcode adds the path).
   Header `Authorization`; type the key, without `Bearer` (Xcode adds it).
   Model `local-main`.
3. **No Claude, Gemini or OpenAI agent** in Intelligence for sensitive repos,
   and none on the host. ACP agents added to Xcode follow
   *External agents (ACP)* above.

"Locally Hosted" does not work here: it takes only a port and sends no key,
and oMLX refuses a request without one. Not verified: whether Internet
Hosted accepts plain `http`. If it refuses, say so in this file rather than
adding a TLS proxy in front of `:1234`.

## Why two tools, and why this matters

The 2026 research on AI-assisted development is not comfortable reading.
Developers using AI assistance scored **17% lower on comprehension** afterwards,
with the steepest decline among those who fully delegated (Shen and Tamkin,
2026). The framing that stuck is **output up, capability down** — and the
distinction between *atrophy*, losing skills you had, and *foreclosure*, never
building them. Roughly half of programmer actions in LLM-assisted workflows show
identifiable cognitive bias, mostly anchoring on whatever the model proposed
first (Zhou et al., 2026).

Nothing ships to address this. The one paper directly on it —
[Agents That Teach](https://arxiv.org/html/2607.06101) — is a design proposal,
not a product. The measurement is years ahead of the tooling.

So the mitigations here are choices, not features:

- **aider shows a diff and waits.** That is friction, and the friction is the
  point. `/ask` and `--no-auto-commits` add more when you want it.
- **Zed's explore profile can't edit.** Reading and discussing without the option
  to apply keeps you deciding.
- **Local models are weaker, and that is quietly protective.** A model that
  cannot one-shot the answer keeps you in the loop — the opposite of how model
  quality is usually discussed.
- **Architect mode separates deciding from typing**, which keeps the design
  decision visible instead of buried in a diff.

None of this is about distrusting the output. It is about noticing when you have
stopped thinking, which by definition is not something you notice.

## Other editors

Not recommended here, recorded so the question does not come round again.
Checked 2026-11-07 by web search; vendor claims, not tested on this host.
Rule 3 applies to all of them: a tool that sends code to a cloud service,
for indexing or an agent, is for non-sensitive repos only.

| Editor | Local models | Cloud by default | State |
|---|---|---|---|
| JetBrains (AI Assistant, Junie) — setup above | Ollama, LM Studio, LiteLLM. Local models can be assigned to features beyond chat. Junie (out of beta June 2026, on ACP) can use them; one JetBrains answer says only from Junie CLI. "Junie Local" bundles its own local model and needs a 64 GB M5 Mac | JetBrains AI subscription or own keys | Most credible second editor for local work. Not benched against oMLX's token auth |
| Xcode 27 — setup above | "Locally Hosted" provider by port (Intelligence settings). Unverified whether it can send oMLX's token | Built-in Claude, Gemini and OpenAI agents with your own keys; ACP agents | Swift only. Locally Hosted at `:1234`, never its cloud agents, for sensitive work |
| VS Code + Copilot | Bring-your-own-model includes Ollama; still needs a GitHub login | Copilot | Works; an extension stack rather than built in |
| Cursor | Custom endpoint possible; earlier it rejected non-HTTPS base URLs | Indexing and search use Cursor's cloud | Not used here |
| Windsurf, Kiro, Antigravity | Nothing found | Agent-first cloud IDEs | Not used here |
| Cline, aider | Any OpenAI-compatible endpoint | No | aider is the second tool |
